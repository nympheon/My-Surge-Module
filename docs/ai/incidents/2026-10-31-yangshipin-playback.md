## 实际做了什么

1. 用户关闭 blackmatrix7 `Advertising_All.list`。运行配置中可见注释，但同两 trace 域名仍命中 anti-AD 的 `REJECT`。只关第一套没有解除这两个域名的拦截。
2. 用户关闭 anti-AD；首次检查仍未应用。用户随后保存并应用，远端原始配置中两条引用均已注释，运行规则匹配也均变为 `ChinaMax_All.list → DIRECT`。
3. 保留规则模式和 `ChinaMax_All.list`。本轮准备时 AWAvenue 与 APP启动页去广告ultra+ 已处于关闭状态，kelee 仍开启；不能将本轮结论推广成所有去广告模块均已关闭。
4. 启动请求与日志流、定期状态/性能采集，再对完成请求读取 HTTP 状态。使用 remote controller CLI；HTTP API 的另一个端口后来测试为拒绝连接，没有将其当作成功监控路径。
5. 远控中途断开，用户确认画面仍正常。用户随后重启 Surge，控制器恢复连接；重启后仍是两套规则关闭、规则模式和相关域名 `DIRECT`。
6. 用户说明播放仍在继续，因此沿原播放起点统计，没有虚构一个重新播放起点。结束时停止本任务的本地采集进程。

## 为什么“能播一会儿”不等于后续一定能播

HLS 播放会持续刷新播放列表并请求后续分片，而不是启动时把整场直播一次取完。某些后续请求失败时，播放器可能先消耗已缓冲内容，之后才表现为停止。此机制见 [RFC 8216 的客户端行为说明](https://www.rfc-editor.org/rfc/rfc8216.html#section-6.3)。

URL 签名过期、签名错误、防盗链、IP/UA 限制或服务端访问控制都可能产生 `403`。阿里云官方[访问控制排障指南](https://help.aliyun.com/zh/cdn/user-guide/access-control-troubleshooting-guide)明确区分这些情况；它描述通用 CDN 机制，不能据此断定央视频这次采用哪一种鉴权方案。

`mtrace`、`btrace` 的名称看起来与 trace/遥测有关，但名称和被广告列表收录不能证明它们的真实业务职责。当前没有取得并分析足以确认职责的解密请求/响应、央视频官方协议说明或客户端调用链。

可待验证的假设包括：播放器某个依赖流程受阻、上报失败引起重试/状态异常、会话校验或播放地址更新受影响；也可能是规则集中的其他条目或独立的 CDN 行为造成。上述都不是本轮已证明的结论。应直接回答用户：**尚未证实“只拦这两个域名，就一定不能持续播放”这个前提。**

## 后续 AI 应如何使用本结论

- 当前使用选择已经确定：默认保持这两套广告规则停用，按偏好提醒用户；不需要为了补全理论解释主动破坏正常播放。
- 如果用户以后主动授权进一步定位，保持频道、网络、其他模块和重启条件一致，每轮只改变一个规则集或一个域名，分别观察超过历史故障窗口的多次播放。
- 在同一时间线中关联真实 `REJECT`、trace 请求是否完成、播放列表/分片状态和用户画面。需要时在用户授权下获取相关接口正文；不要为了抓包全局关闭证书校验或改全主机 MITM。
- `403` 要保留当次响应头、错误正文及时间差再判断，不能把本地稍后重放过期 URL 的失败当作手机当时失败原因。对有 `pre-matching` 的拒绝规则，放行候选必须用当台设备的实际 `rule explain` 验证，不能仅凭文本排列认定绕过成功。
- 远控断开、端口拒绝、主机不可达不等于直播已断网。本轮没有证明先前不可达的根因；重启后恢复连接也不能证明它单独修复了播放。
- 归档只保留脱敏事实、时间线、聚合统计和来源。控制密码、设备标识、账户数据、完整配置、Cookie、带签名的播放 URL、原始抓包和完整日志不随案例发布。
